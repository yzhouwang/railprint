## Problem Statement

A rail fan has no good way to do for trains what 航旅纵横 (Umetrip) "我的航线" and Flightradar24's MyFlightradar do for flights: log which railway line **segments** (乘车区间) you've personally ridden, see them lit up on a map in **real track geometry**, and watch a running **total km + % of the network completed**, with a Spotify-Wrapped-style annual share card. The user wants this for **Japan + China**, built **open-source for the rail-fan community** (乗り鉄 / 高铁打卡), where the line data is a shared asset and distribution is the community itself.

User's own words: *"有没有那种能标出铁路线的app 就是乘车区间这样 … should support japan+china for rail fans … should be like 航旅纵横 / my flightradar."*

## Landscape — does this already exist? (7-agent research, 103 web lookups)

**Verdict: Japan = yes (on data + logic). China = no. Unified Japan+China = nobody.**

- **Japan is "solved" on capability.** [乗りつぶしオンライン](https://www.noritsubushi.org/) is a genuine 航旅纵横-for-rail: per-segment marking, color-coded national completion map, 乗車キロ (km), 乗車率 (%), ranking across ~20k riders, even abandoned lines via a time-machine. [JapanRailNote](https://jprail.web.app/) and [RailLab 鉄レコ](https://raillab.jp/records) also nail segment-marking + completion map + km/%. **The Japan gap is purely UX: web-only, dated, manual entry, no mobile app, no auto-import, no Wrapped share card** — not capability.
- **China is genuinely unsolved.** Nothing joins real 12306 ride history to *actual track geometry* and reports completion %. The three half-answers: (1) WeChat 火车票机票 足迹地图 / 国铁吉讯 auto-import 12306 but draw **airline-style O-D arcs**, no %; (2) 藏火车 / 车票票 are ticket scrapbooks whose own devs admit per-train segment geometry is the *unsolved hard part*; (3) 高铁通 / cnrail have geometry but **zero personal overlay**. V2EX users literally ask *"航旅纵横 does this for flights — why is there nothing for rail?"* — unanswered.
- **Unified "one map of every train I've ridden across Japan AND China" has literally zero incumbent.** The closest multi-country tool, [Travel Mapping Railways](https://tmrail.teresco.org/), makes you edit text `.list` files. Validates the concept, fails the consumer test.

That asymmetry IS the opportunity: Japan-first is a *"better mobile skin + open data + Wrapped"* play; China / the unified map is greenfield.

## What Makes This Cool

The "whoa": you open the app and **your** ridden lines glow across the map in their real shapes — *"12,480 km · 38% of the JR network · 6.2% of China HSR"* — and one tap gives you a vertical Wrapped card to drop on X / 小红书. Four delight axes (the user wanted all four):

1. **The flex map** — real track geometry lit per ridden segment, total km, % national + % HSR completed, share card.
2. **Auto-import** — fill the map with minimal typing (the #1 retention lever; manual entry of a lifetime of rides kills cold-start).
3. **Gamified collection (駅メモ-style)** — collect train models (复兴号/和谐号 CR400AF/BF, Shinkansen N700S/E5…), badges (prefecture/province coverage, line-type variety, "every station on line X"), one-tap GPS check-in habit loop, light leaderboards.
4. **Living community heatmap** — everyone's rides aggregate; *"you're 1 of N who rode this segment"*; crowd-sourced geometry corrections.

## Constraints

- **Open-source, builder/hobby.** Distribution = the rail-fan community (Japan 乗り鉄 / 5ch 鉄道板 / X; China 高铁打卡 on 小红书/微博, V2EX, 贴吧). Not a VC startup.
- **Must survive the maintainer.** The recurring failure mode that killed RailBook, RailChallenge, and 降りつぶし.net is *"the enthusiast tool dies when someone stops paying the server bill."* The design must be cheap-to-run / static-first / self-hostable / data-survives-the-app.
- **Japan-first, China-ready.** Ship Japan first (easy data), but the geometry/import data layer must be country-agnostic from day one so China slots in as phase 2.
- **No proprietary / coordinate-locked map deps.** Everything WGS-84 from OSM/MLIT; avoid Amap/Baidu (GCJ-02 shift + surveying-license).

## Premises (all confirmed by user)

1. Japan-first is a *"better mobile skin + open data + Wrapped"* play, not *"first to exist."* Compete on UX, virality, openness.
2. The novel, no-incumbent prize is **China / unified** — Japan-first is a legit on-ramp *only if* the data layer is China-ready from day one.
3. **Auto-import is the whole ballgame.** v1 must ship at least one low-friction path (Japan: ticket-QR / email-parse + map-drag marking — no clean Suica auto-import exists).
4. **The map is the product and the share artifact.** Core loop = import → see your map + % → share Wrapped. Collection + heatmap layer on top.
5. Open-source means the **geometry + import parsers are the shared asset**; design static-first so it outlives the maintainer.

## Approaches Considered

### Approach A: Static-first offline PWA ("RailPrint")  — judge 7.9
Zero backend. MapLibre GL JS + pre-baked `japan-rail.pmtiles` (MLIT N02 → normalized GeoJSON → PMTiles, served by range-request off a CDN), ridden segments in IndexedDB (Dexie), turf.js distance in a Web Worker, Wrapped card rendered client-side, hosted free on GitHub/Cloudflare Pages. **$0/month, effectively immortal.** Weakness: live heatmap + leaderboards degrade to batch/opt-in.

### Approach B: Static PWA + thin serverless backend + open-data monorepo — judge 7.6
A's offline core plus a strictly-*optional* Supabase/PostGIS layer for sync, live heatmap, leaderboards, `/u/handle` profiles; geometry + parsers in a separate CI-validated monorepo. Gets all four features properly. Weakness: heaviest build; the "optional" backend tempts scope creep that re-introduces the death-by-server risk.

### Approach C: RailLog Standard — "OpenFlights for the rails" — judge 8.0
Ship an open versioned rail-geometry dataset + a human-editable `ridelog` file spec (GTFS-for-individuals) + thin consumers (`npx ridelog render` CLI/Action + reference PWA). Data + format outlive any app; others build on the standard. Strongest community-leverage and immortality. Weakness: slowest to the shiny map; "build a standard and they'll come" can flop; casual fans won't edit YAML.

## Recommended Approach — Hybrid (A spine + C durable assets, defer B)

**Ship Approach A's static PWA as v0 this season, but bake in C's two durable assets from line one:**

1. **Canonical store = an open, versioned `ridelog` file** (YAML/CSV under a published JSON Schema, `spec_version` pinned). IndexedDB/Dexie merely *mirrors* it. → user data survives even the app; other devs can build importers/frontends on the format.
2. **Geometry = a versioned, country-namespaced `rail-geo` package** (GitHub Release + jsDelivr/unpkg CDN tag, WGS-84-normalized, per-namespace LICENSE). → the expensive China moat is insulated from app death, openly forkable; adding China later = a new namespace folder, not a rewrite.

**Defer Approach B's backend entirely** until a live community heatmap *demonstrably* becomes the growth engine — and even then serve heatmap/leaderboards as **static nightly exports** (PMTiles/JSON to the CDN), so *reads* never hit a DB. **Honest caveat (review caught this):** a heatmap still needs a *write* path — somewhere opt-in rides get collected — and that write path *is* the minimal backend. The cheapest version is an **opt-in PR of an anonymized, coarsened ridelog** to a data repo (literally zero server), or a tiny write-only Worker. "Static nightly export" is only the read side. Until that write path exists, the community heatmap is genuinely out of scope — the doc does not pretend otherwise.

**Stack:** Vite + Svelte (static adapter) · MapLibre GL JS v4 · PMTiles (protomaps protocol) · Dexie/IndexedDB mirroring the ridelog file · turf.js in a Web Worker · `<canvas>` for the Wrapped card (v0; defer satori/resvg-wasm) · zxing-wasm for QR (phase 1) · Workbox service worker · GitHub/Cloudflare Pages. Pure-function **resolver lib** (ride-log + pinned rail-geo version → resolved segments + km + %) with ambiguous routings surfaced as warnings, never silently guessed; on a `spec_version` / rail-geo-version mismatch the resolver warns rather than guessing.

**Two corrections from review (load-bearing):**
- **Host PMTiles on Cloudflare R2/Pages, NOT jsDelivr/unpkg.** Range requests (which PMTiles needs) are reliable on R2/Pages but flaky + file-size-capped (~20–50 MB) on jsDelivr/unpkg — a full-Japan archive may exceed those. Use jsDelivr only for the tiny `ridelog` JSON Schema.
- **Offline ≠ range-request.** Range-fetch only speeds first paint. For the "mark a ride on a train with no signal" requirement, the Workbox service worker must **precache the full `japan-rail.pmtiles`** on install. So size it deliberately (target a few MB via tippecanoe simplification at low zoom; full detail can stream when online). Precompute per-segment km at build time so live marking just *sums*, never re-runs turf over the whole network.

**Country-agnostic schema:** `line { id, name, country, class(HSR|conventional|tram…), geometry(WGS-84) }`, `station { id, lineId, seq, name, lat, lon }`. Each country is one per-country build adapter → one `*.pmtiles` + station index. Japan tables stay attribution-only; China (phase 2) inherits ODbL — fine and on-brand for OSS. Unified Japan+China map = loading both PMTiles into the same MapLibre style.

### v0 MVP cut (Japan-only, fully static, zero backend)
1. MapLibre + single `japan-rail.pmtiles` (MLIT N02 geometry + ekidata station ordering): full network dim, ridden segments lit in **real track geometry**. PMTiles is precached for offline (see stack note).
2. **Manual marking, bounded to one line at a time.** Tap station A → tap station B *on the same line*; the ridden segment = the geometry slice between their **ekidata sequence indices** on that line. This is the honest sidestep of the O-D problem: by operating on a single line's station sequence (not arbitrary city-to-city O-D), there's no branching/path-choice to resolve. Multi-line trips = mark each line's portion separately in v0. (Tapping two *non-adjacent* stations on one line is fine — the slice is unambiguous; tapping across lines or where a line branches between A and B is out of v0.)
3. Live **total km + % national + % HSR**, summed client-side from precomputed per-segment km. **Denominator is pinned to the rail-geo version and stated in-app:** national = passenger lines in N02 (exclude freight-only/non-passenger track); HSR = the Shinkansen line-class subset. This number gets screenshotted, so it must be fixed and reproducible.
4. Canonical store = `ridelog` **CSV + JSON Schema** (`spec_version`; defer YAML until a hand-edit use case exists). **CSV import + export from day one** (ingest 乗りつぶしオンライン / RailLab histories → instant non-empty cold-start + trust). **Re-import is a merge**, deduped on a ride identity key (`date` + `line` + `from` + `to`); offer merge-vs-replace on import.
5. **One** vertical Wrapped share card (total km, lines completed, new prefectures, longest ride, most-ridden line) → PNG via `<canvas>` → Web Share.
6. For v0, **commit the normalized PMTiles + station tables straight into the app repo.** Defer the versioned, country-namespaced `rail-geo` *package* (separate Release + CDN tag + per-namespace LICENSE) until phase 2 or a second consumer actually exists — that ceremony is China-future infrastructure, not v0 function. Likewise write the **Japan importer concretely**; extract the country-adapter interface only when China forces a second implementation.

Deferred: all auto-import (QR/OCR/paste-parse), train-model + badge gamification, GPS check-in, community heatmap, China namespace, the standalone `rail-geo` package + adapter abstraction, and any backend.

## Data Sources & Licensing

| Source | Covers | License | Notes |
|---|---|---|---|
| MLIT 国土数値情報 N02 | Japan lines + stations | Attribution-only (NOT share-alike) | JGD2011≈WGS-84; authoritative; clean even for closed use |
| ekidata.jp / 駅データ.jp | Japan station ordering/metadata | Permissive | Station-sequence is key to accurate %|
| ODPT / GTFS-JP | Japan schedules (Tokyo area) | Free + attribution | Optional; Japan-only |
| OpenStreetMap (Overpass/Geofabrik) | **China** lines (phase 2) | ODbL (share-alike) | Only realistic China track source; WGS-84; uneven on newest HSR, inconsistent line-relation tagging → must stitch ways + gap-fill |
| Wikidata / Wikipedia / cnrail | China line inventory (phase 2) | mixed | Drives "what SHOULD exist" for gap-filling |

**Avoid:** Amap/Baidu map APIs (GCJ-02 coordinate shift + surveying-license locked). **China schedules** are an open/legal dead end — keep China to geometry + ridden-segment tracking only.

> ⚠️ **Verify before building (load-bearing).** The whole open-data + redistribution thesis depends on the right to *redistribute a derived, reprojected, repackaged* dataset — not just to *use* the source. The "attribution-only" (N02) and "permissive" (ekidata) labels above are the research's read, not a legal sign-off. Pin the exact current license version of MLIT N02 and ekidata/駅データ.jp and confirm derivative-redistribution is allowed *before* publishing any `rail-geo` artifact. If ekidata's terms turn out to restrict redistribution, fall back to deriving station ordering from OSM/N02 directly.

## Open Questions

- **Verify the Japan data licenses first** (see ⚠️ above) — redistribution rights for N02 + ekidata gate the entire open-data thesis. This is the one thing to confirm before writing the build pipeline.
- **Offline payload budget:** decide the precached `japan-rail.pmtiles` target size (a few MB simplified) and the Workbox strategy, since "mark a ride with no signal" requires the archive to be cached, not range-fetched.
- **Disambiguation UI:** the resolver's warning ("which line did you ride between A and B?") is the main risk surface once auto-import lands — spec the actual UI before phase 1, not just "warns."
- **Biggest risk (all approaches): O-D → geometry snapping.** Mapping a ride onto branching/shared track to compute accurate per-line % is unsolved even by incumbents. **Mitigation already in v0:** start with manual tap-A→tap-B marking (sidesteps O-D inference), lean on ekidata station-sequence ordering, and require explicit `line:` disambiguation with visible resolver warnings — never silent guessing. Revisit before auto-import lands.
- **China import method** (phase 2): screenshot-OCR of 12306 history, e-ticket/paper QR scan + manual confirm, or pursue institutional 12306 OAuth? Determines whether China onboarding is magical or manual. (No open 12306 API; ~30-day history; scraping is anti-bot/ToS-grey.)
- **IndexedDB durability:** it's per-browser and OS-clearable. Mitigate by nagging export and treating the `ridelog` file as canonical, but cross-device sync without a backend stays manual (file export / optional cloud-file) until/unless B is justified.
- **Heatmap feel:** static nightly aggregate is immortal but not live. Acceptable for v1, or is live "1 of N" the actual growth hook? (Decides whether B ever happens.)
- **New-HSR freshness (China):** OSM lags; are you up for ongoing Wikidata/cnrail-driven gap-fill as the China moat?

## Eng Review Decisions (2026-06-23, /plan-eng-review)

Validated against current best practice (5-agent search, 71 lookups) + two independent outside voices (Codex + Claude subagent, strong consensus). Repo scaffolded + pushed: **https://github.com/yzhouwang/railprint**.

**Platform (Issue 1):** Browser **web app first** (online-only v0). Offline + installable PWA = tier-2 fast-follow; native app = tier-3 later. Deletes all PMTiles-offline / service-worker machinery from v0.

**Sequencing (Issue 7, cross-model consensus):** **Import-from-incumbent is the v0 HERO**, manual marking secondary. First real action = a **crosswalk spike**: hand-map ~50 rows of a real 乗りつぶしオンライン/RailLab export to N02/ekidata IDs to prove the only non-manual acquisition path is feasible *before* building.

**Geometry source:** MLIT N02 — confirmed **CC BY 4.0** (better than the doc's caution). Pin a 2024/2025 vintage; ship `出典「国土数値情報（鉄道データ）」（国土交通省）を加工して作成`.

**Stitching (Issue 3):** Required build-time stage — chain N02 RailroadSection by endpoint, flip reversed, validate continuity + station count; un-stitchable lines → checked-in **overrides file** (forkable, community-fixable). lineSlice rejects MultiLineString, so this is mandatory, not optional.

**Station sequence (Issue 2):** ekidata for conventional-line names; **Shinkansen sequence DERIVED from N02 geometry** (project stations onto stitched line, sort by along-distance) — ekidata's free tier lacks Shinkansen ordering. `%HSR` subset keyed off **`事業者種別 N02_002==1`** (not `鉄道区分 N02_001`).

**Marking (Issue 5):** **Line-first** — pick a line, then tap station A → station B; segment = slice between their sequence indices (single-line only, dodges O-D inference). Loop lines (山手線/大阪環状線) store **arc direction explicitly**.

**Trip model (Issue 8):** Single-line slice is the coverage primitive; manual rides can be **grouped into a trip** (diary/card). Auto-decompose (O-D→legs) deferred. Import supplies leg-level data, so v0 is covered.

**Data model (Issue 9, Codex):** **Coverage SET** of ridden segment-ids drives km/% (set-union, dupe/undated-proof); separate **ride-EVENTS log** (date, train model, notes) drives diary + Wrapped card. Fixes the bad `date+line+from+to` dedupe key.

**Storage/durability (Issue 4):** Dexie/IndexedDB = runtime truth; **CSV export = durable backup-of-record** (the only thing surviving "clear data"); ridelog stores **references, not geometry**; resolver **pins rail-geo version + warns** on mismatch; `navigator.storage.persist()` + export-nag. Cross-device = manual import for now.

**Geometry compute (folded):** all turf at **build time** (`lineSliceAlong` + precomputed distance-along, never runtime `lineSlice` on tapped coords); runtime ships **zero turf**, just sums precomputed per-segment km.

**China corridor IN v0 (TODO 2 → promoted to v0):** ship **one small China corridor (京沪高铁)** through the same pipeline from OSM, to validate the country-agnostic schema against China's reality (OSM/ODbL geometry, WGS-84, avoid Amap/Baidu GCJ-02) *before* investing in broad Japan breadth. v0 identity = "Japan + one China corridor."

**Tests (Issue 6):** **golden-file geometry suite** (computed km ≈ published official lengths within tolerance, station counts, loop arcs — build fails on drift) + Vitest unit + Playwright E2E for the core flows.

**Render (folded):** light ridden segments via a single **data-driven style expression** keyed on the coverage Set (not per-feature `setFeatureState`); incremental stats. Outside-voice flag: load-test the **near-complete render** (80%+ lit) — consider inverse render (base = ridden, overlay unridden gaps).

**Deferred to TODOS.md:** rail-geo version **migrations** (N→N+1 ID map + quarantine) before the 2nd data release.
