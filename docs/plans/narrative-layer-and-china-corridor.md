# CEO Plan: Narrative layer (faithful trip diary + train-model capture) + the 京沪 China corridor
Generated by /plan-ceo-review on 2026-06-25
Branch: master (next dev cycle) | Mode: SELECTIVE EXPANSION

## Vision

RailPrint today is acquisition (CSV import, the cold-start hero, already shipped) + a coverage map + a Wrapped card. What it lacks is a reason to open it between trips and an identity/story layer. The map answers "which track have I covered?" It does not answer "what journeys have I taken?" or "what have I ridden?"

The 12-month ideal: open the app, your lines glow, and it tells you *"87 trips · 41,000 km · 23 different trains · Japan + China."* Tap a trip to relive a journey; tap a train to see every time you rode an N700S; and the one map of every train you've ridden across **Japan AND China** has literally zero incumbent. This cycle ships the spine: a *faithful* trip diary (the narrative substrate), train-model capture (so the collection starts accreting content), and one real China corridor (so the unified map stops being theoretical).

## What Already Exists (reuse, do not rebuild)

- **`src/lib/trips.ts`** — `summarizeTrips`/`summarizeDiary`/`tripEndpoints`, aggregates km, lineIds, `trainModels`, date, eventCount per trip. Pure + tested. The diary's render engine. (Becomes faithful after item 0.)
- **`trainModel`** — in `RideEvent`, `markRide`/`markRoute` opts, `db` fields, CSV export/import round-trip, incumbent 車両 column detection. Never captured from a manual user.
- **CSV import** — fully built (parser, fuzzy crosswalk, review-and-resolve, merge/replace, idempotent re-import). Imported rides carry `tripId` + `trainModel`.
- **Country-agnostic schema** — `RailGeoPackage.country`, `RailLine.country`, WGS-84 enforced. `buildRailGeoPackage()` is generic; only N02 ingest is JP-specific. `LineBuildInput` is sparse (no operator/color/logo/rank) — the CN adapter must fill these.
- **`admin-regions.ts`** — already ships `CN_REGIONS` + `regionFor(lon,lat,country)`.
- **Stub `JINGHU_HSR`/`CN_PACKAGE`** — schema proven against a 13-station China line in tests; the real corridor replaces it with pinned-OSM geometry.
- **Map rendering** — multi-package aware.

## Key Findings (3-audit system review + Codex outside voice)

- **FINDING A — data model is the foundation (resolved → item 0).** DB re-stamps segments into the newest trip (`db.ts:59,83`); a faithful diary + per-ride train models require the append-only events log the design intended. Decided: build it first.
- **FINDING B — national % pollutes across countries, and not only on StatsScreen.** `headline` sums `totalKm`/`hsrTotalKm` across packages (`store.ts:130`); the blended % also reaches the **Wrapped card** and the **desktop map side panel** (`App.svelte:62`, `StatsScreen:70`). Per-country must fix all three. `byCountry` already exists.
- **FINDING C — CN attribution is a licensing must.** Visible rail attribution is hardcoded to MLIT N02 + OSM-romaji (`map/style.ts:393`). Shipping CN OSM geometry (ODbL, share-alike) requires surfacing OSM attribution.
- **FINDING D — the OSM corridor is the risk; pin it.** Build the corridor from a checked-in OSM extract (deterministic, reviewable), golden-file against published ~1,318 km, hand-verify first ~5 segments. This IS the "validate the schema against China's messy reality" step.
- **FINDING E — train-model free text → junk.** Needs canonicalization + suggestions + an edit/merge path, from the start.
- **STRATEGIC NOTE (Codex):** a static diary is a *view*, not a retention *loop*. The loop seed here is the train-model **collection progress** + (later) editing/notes/replay. This cycle ships the spine and the first progress hook; the full loop (badges, check-in, notes) stays a deliberate follow-up.

## Eng Review Decisions (2026-06-25, /plan-eng-review)

Reviewed against the live code (`db.ts`, `store.ts`, `import/commit.ts`, `resolver.ts`, `trips.ts`).

**KEY FINDING — T0 is contained; NO schema migration.** The events log is already the single source of truth; coverage is already derived and dedup-by-`segmentId` (`resolver.ts:90`); `segmentId` is a non-unique index (`db.ts:27`); import already appends content-addressed journey-grain events and bypasses the dedup/re-stamp paths (`commit.ts`). The one-event-per-segment constraint lives in exactly two functions: `addRideSegments` (dedup) and `markRouteSegments` (re-stamp). T0 = change those two to append + adjust the guard. Resolver / coverage / import / Wrapped / the diary engine are unchanged. Lower risk than the CEO plan assumed.

**E1 — repeat-mark semantics: soft-confirm append.** Every confirmed mark appends a new trip (N events, fresh tripId), even over already-ridden legs. The hard "この区間は記録済み" block becomes a soft confirm ("log again as a new trip?"). Within one mark action: dedup the slice + a submit/idempotency guard so a double-click can't create two identical trips. Coverage % unchanged (dedups). Both mark paths behave identically.

**E2 — sequencing: two PRs, narrative first.** PR A = T0+T1+T2 (events-log + diary + capture). PR B = T3+T4+T5 (China). They share no code (T5 lightly touches `store.ts`, sequenced after T0). Maps to split-labor (one lane per PR).

**Build details (no separate decision):**
- `addRideSegments`' concurrency txn dedup becomes per-ACTION dedup + a content/submit idempotency key, not global-by-segment.
- Rewrite the now-stale comments in `db.ts`/`store.ts` that justify the dedup/re-stamp via the v0.2.0.0 bug — E1 reverses that rationale (diagram/comment maintenance, same commit).
- `MarkResult.added==0` + the "already recorded" UI copy move to the soft-confirm path.
- T5: render `headline.byCountry` (JP default) in StatsScreen, the Wrapped card, AND the desktop side panel; surface OSM/ODbL attribution when a CN package is present.

**Test plan (the diagram):**

## Design Review Decisions (2026-06-25, /plan-design-review)

PR A's two new surfaces reviewed against the established DESIGN.md system (emerald, folder-tab cards, dioramas, Noto Sans JP). APP-UI classifier; no AI-slop hard rejections. Design completeness 5/10 → 9/10.

**D1 — hierarchy (統計):** order = `全国/新幹線 StatCards` → `記録` (superlatives) → **`旅の記録` (NEW FolderTabCard)** → `Wrapped`. The coverage flex stays the screenshot hero; the diary sits between the at-a-glance number and the share CTA.

**D2 — diary rows: date-led.** The DATE is the primary identifier on every row, so a repeat journey reads as two distinct dated trips, not a dupe. Row = `日付 · 東京 → 大阪難波 · 1,318km · N路線 · N区間`, with train model(s) as a `Pill` chip when present. Baseline-aligned rows inside ONE `FolderTabCard` (reuse `.row`/`.rowval`), never a card mosaic.

**D3 — diary empty state:** reuse the warm zero-state pattern — `Diorama` (board) + muted copy ("まだ旅の記録がありません。区間をマークすると、ここに旅がたまっていきます。") + a `Pill`. Not "No items".

**D4 — capture + repeat (mark panel):** inline optional `車両 (任意)` field after station B — a text input with recent-model `Pill` chips above it, fully skippable; the mark button stays primary and records with or without it. For a fully-ridden slice the primary button relabels to `もう一度記録` with a quiet `この区間は記録済み` note (NO modal); the success toast carries an undo. Model also shows on the diary row + the confirmation toast.

**D5 — responsive/a11y:** works in the 380px side panel + mobile (`max-width:460`, `overflow-wrap:anywhere`). 44px min touch targets on tappable rows/chips/buttons; the `車両` field uses a real visible `<label>` (no placeholder-as-label); keyboard + aria-label on the soft-confirm button + model chips; emerald only ≥24px (km figures), emerald-800 for smaller emerald text.

**Interaction-state table:**
```
SURFACE        | EMPTY                      | TYPING/PARTIAL        | POPULATED / SUCCESS                  | REPEAT
旅の記録 diary | Diorama+copy+Pill (warm)   | —                     | date-led rows in one FolderTabCard   | two dated rows (date disambiguates)
車両 capture   | placeholder + recent chips | free text / chip pick | model on row + toast                  | button → もう一度記録 + 記録済み note + undo
```

**Deferred (TODO):** diary density at scale — ship flat reverse-chronological date-led rows; add month/year section headers (and optionally a ×N repeat rollup) when a heavily-imported list exceeds ~50 trips. Not needed for v1.
